## 偏离及理由（规范中的“应”条款）

1. **默认领域配置为 `ml-v1`**，附录 A1 示例中为 `generic-v1`。理由：本产品以 AI 领域为主。识别出的领域与所选配置不一致时会给出警告。
2. **协调器是 SQLite 的 `BEGIN IMMEDIATE` 写锁，而不是常驻进程。** 每个 CLI 调用都在短事务里完成状态转换，效果与单写入者相同。网络盘或同步盘上的锁可靠性没有保证（见 README）。
3. **`Finding.extensions`** 保存 issue_type、action_type、neutral_question 等辅助字段，`PaperSummary` 不属于附录 A3 的实体（存放在 runs.summary_json）。两者都按规范 §5.2 的命名空间扩展处理，不改动 A3 的业务键。
4. **最终报告只用确定性模板**，不让模型润色。这符合 B2 中“润色失败时可直接导出确定性模板”的路径，彻底避免写作阶段把判断升级。
5. **token 在 interactive 模式下只作为目标值**（advisory_estimate），不阻断任务领取。内核实际卡住的是任务数、尝试次数、检索次数、外部全文数、下载字节数和主动时间（§3.1、§6.1）。

## 尚未实现（按里程碑）

- **整个 Run 的 managed 执行与 `reservation_bounded` 费用控制：** interactive 模式下，所有任务已经可以交给内核启动的 Worker 执行（`sreview auto`，引擎为 `claude -p` 或 `codex exec`）。但 `execution_mode=managed` 仍在 plan 阶段返回 `missing_capability`，费用也只是事后上报，没有预留上限（M3）。
- **MCP STDIO 服务：** 服务函数已与 CLI 共用（`interfaces/service.py`），MCP 外壳还没加（M3）。
- **解析能力不足：** 不支持 LaTeX、DOCX、OCR，表格没有单元格结构，PDF 不能渲染回看，没有 bbox。目前只能从文本 PDF、Markdown、TXT 抽取纯文本，图中的数值读不到（M1 余项和 M4）。
- **代码相关：** 没有代码索引、静态检查和隔离沙箱实验执行。reproduction 档只生成 ExperimentPlan（M4）。
- **跨版本：** 跨版本复用、stale 传播（E06）、主张/表格/代码的跨版本匹配都没做。`compare` 只比较文本块（M4）。
- **E02 远程调用结果未知、E13 进程树终止：** 只在 managed 模式下才会用到。
- **Codex 引擎未在真实 CLI 上验证：** 按 `codex exec --json --sandbox read-only --output-last-message` 的公开接口实现，测试使用模拟输出流。本机没有安装 codex，首次真实运行需要确认参数和事件格式。
- **学术质量评测（§16.4）规模不够：** 规范要求 30 个评测集合、双人标注，并给出精确率和召回率。目前只做过 4 篇论文、14 个植入缺陷的小规模评测，见下文，**不能宣称审稿质量已经达标**。

## 真实论文试运行（2026-11-22，arXiv 1706.03762，quick，作者模式，Claude Code 担任宿主）

完整流程跑通：导入 PDF、理解（12 条主张、4 个审查假设）、数值核验（9 项）、4 项检查、文献检索（arXiv，摘要级）、3 次复核、导出。12 条主张的原文锚点全部 exact，宿主提交没有被拒。

- 报告给出 6 条证据充分的优点、5 条已确认的 minor 问题、2 条待澄清事项。准备度为 `not_assessed`，原因是 quick 的任务预算用尽，评测协议检查未完成，这一点在报告中如实列出。
- 程序复算发现原文中的两处真实不一致：EN-FR BLEU 在摘要与表 2 中为 41.8，第 6.1 节为 41.0；第 6.3 节称除 RNNG 外优于所有此前模型，但表 4 中 Luong et al. 2015 为 93.0，高于 92.7。另有 7 项复算支持原文，包括训练 FLOPs 3.3·10¹⁸ 与 2.3·10¹⁹。
- “检查点平均 / 标签平滑影响归因”这一 major 疑点经同一会话复核后保持未确认，等待人工核对，符合 E15。

这次试运行暴露并修复了以下问题（均已补回归测试，见 `tests/test_real_pdf_regressions.py`）：
1. 跨行连字符被删除（`English-\nto-German` 变成 `Englishto-German`），导致原文引用无法锚定。现在引文匹配忽略连字符。
2. `2014 English-French …` 被识别为标题；参考文献之后的附录图被标成 reference；页码混入正文块；图中逐词文本没有标为低质量。
3. 解析器版本没有纳入 PaperVersion 身份，同一 PDF 重新导入时沿用了旧的解析结果。
4. 数值模块不支持非百分比的舍入比较（如 BLEU）、科学计数法的舍入区间、不等式类主张（如“超过 2 BLEU”），也没有乘积与比值运算。
5. 预算池语义错误：复核消耗挤占了分析配额。现按规范 §10.2 分池计算。
6. arXiv 查询的各个词之间是 OR 关系，结果偏题；现改为 AND 并去掉停用词。
7. 报告措辞：数值发现的模板、附录状态与待人工确认的提示没有本地化，限制条目重复，“不允许新增实验”在用户未设定时也会出现（默认值改为允许）。

8. `doctor`：找不到 CLI 时能力记为 unknown 而非 unsupported；在桌面版中通过 `$CLAUDE_CODE_EXECPATH` 找到内嵌的 Claude Code，在宿主会话内运行时直接记录 interactive_skill=supported。
9. 中文报告头的“主要限制”、预算控制等级、覆盖状态和修改计划的标签均已本地化。存储的记录保留稳定的英文消息，只在渲染时翻译。

## 第二次试运行（2026-11-22，一篇未发表稿件，standard，会议审稿模板）

19 个任务全部执行（理解、数值、12 项检查含 LLM 子领域检查、文献、3 次复核），24 条主张全部精确锚定，20 项数值复算全部一致。报告给出 14 条优点、19 条已确认 minor 问题、3 条待人工确认的 major 疑点、1 条待澄清。准备度为 `not_assessed`，原因是 8 条核心主张中有 1 条没有任何检查给出评估（宿主遗漏），报告如实显示 7/8。

这次试运行暴露并修复了以下问题（均已补回归测试）：
10. ICLR 等审稿模板的页边行号（每页 54 个）和页眉“Under review as …”混入正文，会破坏引文锚定并可能让行号被当作数值输入。现按“连续递增的纯整数行 ≥ 10”和“出现在 40% 以上页面的行”剔除（`ingest-0.1.2`）。
11. 数值复算只考虑声称值的舍入区间，没有考虑输入本身也是舍入值，两位小数表格的差值会被误判为矛盾（66.79 − 91.47 = −24.68 对印刷的 −24.69）。现对输入做舍入区间传播；输入可以字符串形式给出以保留印刷精度，字符串输入同样做原文校验（`numeric-0.1.2`）。
12. 报告头把稿件内附录显示为“附录未提供”；现识别参考文献之后的附录章节并显示分析覆盖。“主要限制”中混入了“复用已导入版本”和解析清理说明，现已过滤；拒入原因码去重并本地化。

另记：`sreview plan --paper-version` 单独使用时会因缺少 `input.manuscript` 被拒（已在第三次试运行时修复）。任务租约为 30 分钟，宿主阅读长稿件时可能超时，需重新领取（会消耗一次尝试）。

尚未处理：报告阶段不会由数值记录重新生成措辞，历史 Run 保留创建时的文本；`allow_new_experiments` 的默认值已改为 true，但此前规划的 Run 仍保留当时的设置。

## 第三次试运行（2026-11-23，Skill 无人协助自跑）

在一个只装了 Skill 和 `sreview` 的空目录里，用全新的无头 Claude Code 会话执行 `/paper-preflight paper.pdf`（arXiv 1706.03762，quick，中文），全程没有人工介入。会话自行完成 doctor、plan、run、领取和提交任务、导出，没有违反证据纪律或外发限制，还主动指出这篇 PDF 是已发表论文、不像作者本人的投稿稿。耗时约 9 分钟，费用约 2.7 美元。

问题：9 项任务只完成 2 项检查，运行以 partial 结束，核心检查全部被拦下。原因如下：
13. quick 的分析阶段只有 600 s × 70 % = 420 s，而交互宿主做一次理解任务约 150 s，每项检查约 120 s。quick 计划在交互模式下本来就装不下。现在 plan 会给出 `time_fit` 估算，装不下时警告“expect a partial report”，Skill 会在开始前告诉用户。
14. 复核任务一生成就排在待做的分析任务前面，占掉分析时间。现在领取时先分析、后复核。
15. 已经做完、只因校验被拒而重交的任务，被分析阶段时间门挡住，白白丢掉。现在重试可以使用复核时段。
16. 停止原因只显示为 `budget`，宿主把 token 目标值的提示误读成停止原因，并告诉用户“同意提高 token 预算即可继续”。实际上 token 只是目标值，不阻断任何操作；提高 token 也不会重开任务。现在 claim 和 status 返回 `budget_stops`，写明是哪个时间阶段上限；Skill 说明了正确的继续方式：`budget set` 设置 `max_active_seconds`，然后 `resume`。

修复后用同样的命令在新目录重跑（约 9 分钟，约 3.0 美元）：完成的检查从 2 项增加到 5 项（理解、数值、主张-证据、实验有效性、新颖性定位），3 项复核全部完成。会话正确报告停止原因为“427 s 达到分析阶段上限 420 s”，并给出正确的继续方法（同意新的有效时间总额后续跑）。新暴露的问题：
18. arXiv 和 OpenAlex 当时都对本机返回 429（OpenAlex 给出 Retry-After: 36），宿主随即放弃，文献对比没有做。现在错误信息里带上等待秒数，Skill 规定 60 秒以内等待一次后重试。
19. plan 的警告里已经有“expect a partial report”，但宿主没有在开始前告诉用户（Skill 遵循偏差，最终报告如实说明了）。

决定（2026-11-23）：保留 quick 的 10 分钟上限，缩减检查项。quick 只做理解、数值复算、主张-证据对应和最接近的相关工作四项任务，不做领域专项检查和 AI 子领域追加检查（plan 会给出提示），对应规范中 quick 的“聚焦检查”范围。宿主耗时估算按两次自跑的实测值校准（理解约 140 s、数值约 70 s、检查约 90 s、文献约 110 s），四项合计约 410 s，在 420 s 的分析阶段之内，但余量很小；论文更长时仍可能是部分报告。领域检查需要选 standard 或更高档位。

## 隔离复核 Worker（2026-11-23，M3 的第一部分）

交互式 Run 可以把复核任务交给内核启动的 `claude -p` 进程执行：`sreview plan ... --verify-worker claude [--worker-model M]`，然后运行 `sreview worker verify --run <id>`。宿主领取任务时会跳过复核任务，并在 claim 结果里给出 `waiting_on_worker` 和下一步命令。

- **隔离方式：** 每个复核任务使用一个新的临时目录，里面只放 instructions、context（不含候选结论）、output_schema 和带标注的稿件。启动参数为 `--tools Read`、`--strict-mcp-config`、`--setting-sources local`、`--no-session-persistence` 和 `--json-schema`，stdin 关闭。实测表明，读取目录外的文件会被宿主拒绝，自动记忆指向一个新的空目录。
- **独立性由内核判定，不采信 Worker 的自述：** 内核检查事件流里的 init 事件（工具集、MCP、cwd）、每次 Read 的路径和 permission_denials，全部通过才记为 `fresh` 和 `blinded`。否则结果仍然收下，但记为 `inherited`，不能确认 major 问题。`fresh` 的复核记录会注明“同一模型家族的新上下文，不是统计独立的审稿人”（规范 §8.9）。
- **主动权在内核：** CLI 的 `task submit` 无法提交 Worker 证明。只有 `adapters/worker.py` 通过内核接口传入。Worker 证明只接受复核任务。
- **失败处理：** Worker 超时或没有结构化结果时，立即释放这次尝试（计入尝试次数），不会卡在 30 分钟的租约上。临时目录里的稿件副本用完即删。Worker 的 token 和费用按实际上报值结算，并写入 `isolated_worker` 事件。
- **未做：** `--bare` 模式需要 ANTHROPIC_API_KEY，订阅登录下无法使用，因此用户级插件和 Skill 列表仍会加载，但没有可用的工具去调用它们。codex Worker 还没有适配。整个 Run 的 managed 调度也还没有做。
- **真实运行（第四次无头自跑，quick，Transformer 论文）：** 宿主自己加上 `--verify-worker claude` 完成 4 项分析任务，claim 返回 `waiting_on_worker` 后调用 `sreview worker verify`。4 个 Worker 全部通过隔离检查（`fresh`，`blinded`），每个约 25-37 s、0.24-0.36 美元，合计 1.24 美元。Worker 独立确认了 41.8/41.0 和 Luong 93.0 两处问题，但把 BLEU 不一致的影响评为 minor 而非 major，准备度因此是 `conditional`，而不是此前同会话复核时的 `blocked`。这是独立复核的预期效果：结论可以和发现者不同。
  暴露并修复了以下问题：(a) 宿主把 `worker verify` 放到后台执行，`-p` 会话随即结束，Worker 在会话外跑完，但宿主没能导出和总结。Skill 现在要求前台执行，`--max-tasks 4`，超时设为 10 分钟，必要时重复调用。(b) 数值复核追加“+ deterministic recomputation”时覆盖了“isolated worker”前缀。(c) 报告头仍写“同一宿主的复核不能单独确认重大问题”，现在按是否启用 Worker 分别说明；quick 的范围说明已本地化。
- **测试：** `tests/test_isolated_worker.py` 用模拟事件流覆盖：能确认 major、多余工具/越界读取/权限拒绝时降级为 inherited、无结果时释放尝试、未开启时拒绝、非复核任务拒绝 Worker 证明。

## 一条命令运行与分析 Worker（2026-11-23）

`sreview auto --manuscript ... --effort <e>`：内核用短命的 `claude -p` Worker 执行全部任务，包括理解、数值、各项检查、文献检索和复核，然后导出报告，只返回一份精简的 JSON 摘要。每个 Worker 只接一个任务，任务材料通过 stdin 传入，`--tools ""`，不带 MCP、设置和会话历史。文献任务分两步：先由 Worker 提出只含公开概念的检索词，内核执行检索（照常做外发拦截和预算记账），再由第二个 Worker 根据检索结果做判断。每次调用最多工作 7 分钟（`--slice`），没做完就返回 `next`。被拒的结果会带上内核给出的错误清单交给下一次尝试。Worker 按 max_concurrency 并行运行。Skill 默认走这条路径，手动模式只作后备。

实测（Transformer 论文，quick，全新无头会话）：

| 方式 | 主会话调用 | 主会话输入 | Worker 输入 | 合计输入 | 费用 |
| --- | --- | --- | --- | --- | --- |
| 全部在主会话里做（自跑 3） | 28 | 3.16M | — | ≈3.2M | $2.83 |
| 分析 Worker + 主会话循环（自跑 6） | 23 | 1.55M | 0.17M | ≈1.7M | $3.14 |
| `sreview auto`（自跑 7） | 5 | 0.22M | 0.19M | ≈0.41M（−87%） | $2.39 |

现在费用主要花在 Worker 上（6 个 Worker 共 $2.00，Opus，输入无法复用缓存，输出 29k）。`--worker-model sonnet` 预计可以把这部分降到约五分之一，但质量还没评测。主张-证据检查的第一次结果被拒，带上错误清单重试后通过。41.8/41.0 仍在报告里出现两次，跨模块去重规则没有覆盖到这种情况，待修。

## 数值误报修复（2026-11-23，`numeric-0.1.3`）

在真实稿件上看到的误报来源及修法：
1. 百分数显示的比值（"93.18%" 对比算出的 0.9318）被当成单位不一致。现在当算出值是分数时，带 % 的显示按比值比较（`display_unit`）。
2. 输入末尾的 0：0.958 在原文 "0.9580" 中找不到。现在小数后允许补 0，整数允许 ".0"，但 "12" 仍不匹配 "120"。很小的数（3.6e-05）同时按 0.000036 的写法匹配。
3. macro-F1 的定义不同：很多论文用宏平均 P 和 R 计算 F1。`confusion_metrics` 现在同时给出 `macro_f1_of_macro_pr`，两种定义任一吻合即判为支持，并注明用的是哪种。numeric 提示词要求输入按原样写成字符串，并且不要用 `mean` 去检查 macro-F1。
4. 含负数的 `mean`/`sum` 之前不做输入舍入传播，现在做了。`mean` 和 `sum` 对每个元素都单调，只有含负数的 `product` 不做。
5. 跨模块去重：以"来自数值模块"（`check_type == numeric.consistency`）认定权威发现，不再看 issue_type。检查模块把自己的发现也标成 numeric 时，之前会漏掉去重。

用已存的数值任务结果重放（不调用模型）：
- 非公开评测稿件 A：数值标记 12 → 7。植入的 A1–A4 全部检出，其中 A1、A3 以前只是"无法核实"，现在判为矛盾。剩下 1 条是定义误报（用 mean 检查 macro-F1，新提示词已禁止），另有 1 条疑似稿件本身的问题。
- 非公开评测稿件 B：11 → 5。植入的 B1–B3 全部检出（B2、B3 以前只是"无法核实"），另有 2 条关于稿件本身的检查点一致性疑点。
- Transformer 论文的各次运行：标记不变，都是真问题。

## 公开论文质量评测（2026-11-24，植入缺陷，quick，Sonnet Worker）

两篇 arXiv 论文：ResNet 1512.03385 和 BatchNorm 1502.03167。用 pypdf 抽取文本后植入 7 个缺陷：5 个数值缺陷，2 个结论与证据不符的缺陷。答案另行保存，Worker 看不到。运行方式：`sreview auto --effort quick --worker-model sonnet`，cutoff 设为原文发表日期。

| 论文 | 检出 | 报告条目 | 有用条目 | 噪音或错误 | Worker 费用 | 用时 |
|---|---|---|---|---|---|---|
| ResNet | 4/4（R1–R4） | 8 | 7 | 1 条"无法核实"的问题 | $1.10 | 177 s |
| BatchNorm | 2/3（B1、B3） | 8 | 5 | 2 条"无法核实"的数值问题，1 条子论断有误 | $0.91 | 194 s |
| **合计** | **6/7** | 16 | 12 | 4 | **$2.01** | 两篇并行 |

- 漏检：**B2**（"0.060 (30 times that of Inception)"，应为 0.045）。数值抽取没有选中这处。
- **B1** 由 claim-evidence 检查发现，数值模块没有判出来。原因是 PDF 把 `31.0·10^6` 抽成了 "31.0 · 106"，输入无法解析，结果只报了"无法核实"。
- **子论断有误：** B3 的发现附带说 "BN-x30 文中 6M 与表中 2.7M 不一致"。其实两者分别是达到 74.8% 和达到 72.2% 的步数，并不矛盾。
- **评级：** 植入的数值矛盾都被评为 minor。在投稿前自查的语境下可以接受。
- **两次运行都是 partial，ResNet 的 readiness 为 `not_assessed`。** 原因不是预算，而是 Worker 自报覆盖不完整。quick 几乎总会落到这个状态，对用户有误导，需要改。
- **成本对照：** 上次 Opus Worker 的 quick 一次约 $2.39（含宿主），这次 Sonnet 每篇约 $1.0。在这个规模上，检出率没有看出下降。
- **局限：** 样本很小，只有 2 篇论文、7 个缺陷。两篇都是名篇，模型可能记得原文数字，检出率可能偏乐观。

### 针对评测缺口的修复（2026-11-24，`numeric-0.1.4`）

1. **科学计数法：** 现在能读 "31.0 · 106"、"3.3×10¹⁸"、"5 · 10^-3"。前一种是 PDF 把上标压平后的样子。只认中点和乘号，"2 x 106" 仍按字面处理。尾数的精度保留下来，用于舍入区间。重放 BatchNorm 的已存结果：B1 的 "14 times" 由"无法核实"变为**矛盾**。
2. **倍数与系数：** 数值抽取提示词新增一条，要求核对文中所有 "N times"、"a factor of k, to v"、"(30 times that of X)"，方法和设置部分里的超参数也包括在内。B2 这类缺陷要等真实重跑才能确认能否检出。
3. **核心论断全覆盖：** `core.claim_evidence` 必须给每条核心论断一个评估。漏掉时，内核第一次退回并列出漏掉的 id；重试仍然漏掉，就记为 `not_checked`，并注明"检查在重试后仍漏掉"，不会循环。ResNet 那次 9 条核心论断只评了 7 条，所以 readiness 是 `not_assessed`。readiness 的判定规则没改：真漏检时仍然如实报告。
4. **已知仍存在：** ResNet 定位误差那条，Worker 取错了输入（26.9/8.9，原文是 25.3/9.0）。内核发现输入不在引文中，只报了问题，没有误判为矛盾。

## 文献回退、partial 语义、审稿表单、Codex Worker、版本控制（2026-11-24）

1. **文献检索回退**（`adapters/worker._search_all`）：
   - 某个查询失败后，换另一个**已获许可**的 Provider 重跑一次，绝不使用未许可的来源。
   - 同一 Provider 失败两次后，剩下的查询不再发给它（熔断）。
   - 每次 arXiv 请求至少间隔 3 秒，arXiv 的超时放宽到 35 秒。
   - 查询规划的提示词要求把查询分散到各个 Provider。
   - 起因：ResNet 那次运行的 4 个 arXiv 查询全部超时或被限流，OpenAlex 一次都没被尝试。
2. **partial 只表示真实缺口：**
   - 任务里的 `not_checked` 改记为范围说明（`scope_notes`），例如图中数值无法读取、没有代码。
   - 只有内核按任务类型判定的 `blocking_gaps` 才会让任务成为 partial：
     - claim-evidence 有核心主张没有评估；
     - 文献检索没有一次成功；
     - 复核没有覆盖全部发现；
     - 检查什么都没看。
3. **审稿表单草稿**（新任务类型 `assess`）：
   - 触发条件：审稿模式，提供了有效的会议表单，并且加了 `--scores` 或 `--recommendation`。所有检查和复核结束后，内核再追加这个任务。
   - 内核会拒绝以下提交：
     - 分值不在表单量表内，或标准不存在；
     - 必填标准没有给分；
     - 引用了未进入报告的发现；
     - 没有已确认的 major/critical 问题却选择最负面的建议；
     - 存在已确认的 critical 问题却选择最正面的建议；
     - 建议没有引用它所依据的严重问题。
   - 评分、建议和给编辑的保密意见只出现在审稿人私有视图和编辑视图中，给作者的视图里没有。
   - 没有表单时不会生成评分，量表也不会凭空编造。
4. **Codex Worker：**
   - `--analysis-worker codex` 和 `--verify-worker codex`；`sreview auto --host codex` 默认使用 codex 引擎。
   - 运行方式：`codex exec --json --skip-git-repo-check --sandbox read-only -C <临时目录> --output-last-message`，任务包通过 stdin 传入。
   - 输出 Schema 写在提示词里，不走结构化输出参数。原因是 Codex 的严格 Schema 表达不了自由格式的数值 `inputs`。模型返回 JSON 后由内核解析和校验，被拒时带着错误列表重试。
   - Codex 保留了只读 shell。只有事件流里完全没有工具调用（命令、MCP、文件修改、网页搜索）时，复核才记为 `fresh`，否则记为 `inherited`。
   - Codex 只上报 token，不上报费用。
5. **版本控制：** 项目已用 git 管理。未发表稿件的试运行报告（`trial_reports/`）和安装生成的 `.claude/` 都在 `.gitignore` 里；状态文档里与保密稿件相关的细节已经去掉。

测试共 84 个，全部通过。

## standard 成本修复（2026-11-24）

两篇非公开稿件的 standard 审稿每篇花了 $7.2–7.8（Sonnet Worker）。拆开看，58% 花在复核，32% 花在检查：
- 复核调用了 25 次，每次只复核 1 条问题，却都要重发整篇稿件（约 44k token）。
- 每次调用都按写缓存的价格计费（约 $3.7/M），几乎没有命中缓存。

修法：
1. **稿件放进系统提示**（`--append-system-prompt`），任务相关的部分仍通过 stdin 传入。用 Haiku 做了实测：稿件只放在用户消息开头时，第二次调用仍要整段重写缓存；放进系统提示后，第二次调用从缓存读取 13.1k token，费用降到第一次的约 1/7。带 `--json-schema` 时同样能命中。稿件超过 40 万字符时退回 stdin。Codex 把共享部分放在最前面，依靠 OpenAI 的前缀缓存。
2. **预热：** 同一引擎、同一任务类型的第一次调用单独运行，先把缓存写好，其余调用再并行开始。
3. **复核批量化：** 一次提交产生的待复核问题，每 6 条合成一个复核任务（`VERIFY_BATCH`），不再一条一个任务。

按上一次运行的用量估算，每篇约 $2.5–3，降幅约 65%。还没有真实重跑来确认。之后成本的大头会是检查的输出 token。
